# From evidence to a buildable recommendation

Choose a pattern because it fits the goal and context. Do not decide by a vote
among screenshots. Read [goals](goals.md) for evidence types and
[flows](flows.md) when behavior spans screens.

## Pattern selection

For each consequential candidate, record only what affects the choice:

- Problem and circumstances where it helps.
- Underlying rationale, with a source principle when it adds substance.
- Observed implementation and source, if available.
- Prerequisites, costs, failure conditions, and an alternative.
- Fit for this audience, data, platform, and experience goal.

Distinguish an observed convention, a useful exception, purposeful expression,
and irrelevant decoration. A new synthesis is valid; identify what remains to test.
Neither familiarity nor originality is an automatic virtue.

Explain the mechanism concretely: what does this expose, group, preserve, or
clarify, and which burden might that reduce? Compare the strongest plausible rival
with the same audience, content, and state. Resolve competing principles by
context—disclosure versus comparison, guidance versus practiced efficiency,
expression versus attention. Preserve contradictory observations and state what
new evidence would reverse an important recommendation; do not invent scores or
vote by app/citation counts.

A reference is raw material. Retain its useful mechanism while correcting weak
copy, hierarchy, information order, state feedback, or visual execution. An
original treatment can outperform the available precedents; show what it improves
and verify those properties. Claims about better user outcomes require user
evidence. Guidelines are contextual reasoning aids, not a ceiling or automatic
verdict. Keep normative platform requirements and approved product constraints
distinct from heuristics and taste. When a heuristic conflicts with a better
solution, name the tradeoff, preserve its underlying purpose where relevant, and
check the result rather than forcing compliance.

## Brief and direction

A significant brief contains the user goal, known evidence/assumptions, scenario,
flow/state contract, visual idea, and acceptance criteria. Use
[the packet template](../templates/design-packet.md) rather than creating separate
repetitive documents for each step.

Keep criteria observable:
- **Visual:** which information leads, what is grouped, hierarchy and density,
  legibility, and coherence with neighboring screens.
- **Behavioral:** action and response, carried state, feedback, completion,
  correction/recovery, and accessibility paths.

Directions solve the same job with the same content. Describe the strongest case
and cost of each, then recommend one. Migration effort is a separate consideration
from UX quality. Do not weaken alternatives to make the recommendation look better.

For example: “I recommend A because returning users can compare the relevant
figures without reopening details. B is quieter but hides that comparison. The
remaining taste choice is whether A feels too dense with our real content.”

## System mapping

Map components, content roles, tokens, assets, interaction semantics, and motion
to the existing system. A recurring unmet need can justify a reusable addition.
For a new product, establish a small coherent system from the chosen direction;
absence of tokens is not a reason to stop or borrow a competitor's brand.

Preserve the selected mechanism in the build criteria. Connect consequential
observations and source principles to the adaptation, remaining assumption, and
check. If the rationale is comparison without recall, verify that relevant labels,
values, units, and qualifications remain available with real content and supported
text sizes. If it is continuity, exercise the named exit and return with partial
work. Reconsider the choice when implementation removes the property that made
it useful. Visual resemblance and token compliance do not establish success.
